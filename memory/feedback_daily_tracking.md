# 日次記録・報告の仕組みの学習

## 1. フォロー・フォロー返しは報告トリガーが無く、実施していても記録が漏れる

- 失敗例 (2026-07-19): ユーザーは実際にフォロー実施・フォロー返しの受領を継続的に行っていたが、
  いいね（スクショ添付で自動記録）・リプ（「送りました」で自動記録）と違い、フォロー系には
  自動記録トリガーも定期的な確認質問も無かったため、本人が「言い忘れていた」ことに後から気づくまで
  一切記録されなかった。
- **Why:** 「言われたら記録する」受け身の仕組みは、報告する側が毎回思い出さないと機能しない。
  いいね・リプは既に「言わなくても分かる/言うタイミングが決まってる」形にしてあるのに、
  フォロー系だけ例外的に「本人が能動的に言う」ことに依存していたのが構造的な欠陥。
- **How:** 送信報告（「送りました」等）を受けたタイミングで、**毎回こちらから**
  「フォローした人・フォロー返しがあった人はいますか？」と確認する（CLAUDE.mdに明記）。
  受け身で待たない。返答が「なし」でも良いので、必ず一往復のやり取りに含める。
- **記録先の使い分け（混同しないこと）**:
  - `daily_activity_log.csv`（`npm run today -- --done follow`）＝ 自分が誰かをフォローした実施回数
  - `reply_outreach_log.csv` の `follow` 列（`npm run reply-log -- --update ... follow=1`）＝
    相手が自分をフォローし返してきたか（コールドリプの転換率そのもの。週次のtier分析に直結）
  - 同じ「フォロー」という言葉でも主体が逆なので、報告を受けたらどちらの向きか確認してから記録する。

## 2. データ入力コマンドの重複行に注意

- 失敗例: `--done reply target_url=...` や `--add target_url=...` を、既に手動で追記済みの
  行に対してもう一度実行すると、重複行が生まれる（お嬢/Lonely3699、DuelistWwで発生、2026-07-10・07-19）。
- **How:** 記録コマンドを打つ前に、対象の `target_url` が既にCSVに存在しないか
  `grep` 等で確認する。重複が発覚したら空欄側や情報の薄い方を削除して1行に統合する。
