## 3. 重複の指摘と修正案

### 3-1. `.claude/skills/` と `.codex/skills/` の完全二重管理（8 Skill × 2）

diff で全8ファイルが同一と確認済み。今は一致しているが、片方だけ更新すると Claude と Codex で違うルールが走る。

**修正案（推奨順）:**
1. `.claude/skills/` を正典とし、`.codex/skills/` は各ディレクトリを symlink にする（git は symlink を保持できる。Codex が symlink を読めるかは1回だけ動作確認）。
2. symlink が使えない場合: `scripts/sync_skills.py`（.claude → .codex へコピー）を作り、`npm run sync-skills` を Monthly Workflow に追加。加えて diff チェックを validate に組み込み、乖離したら警告。

`.claude/agents/*.md` と `.codex/agents/*.toml` も同じ役割の並行定義（形式が違うので symlink 不可）。こちらは **AGENTS.md の「AI Organization Roles」を正典と明記し、agents ファイルには役割1行＋正典参照のみ残す** 運用で乖離コストを下げる。

### 3-2. 「切り口5角度」テーブルの三重記載

同じ5角度（記憶のズレ/入力の面倒さ/続行理由の変化/店・台選び/UI思想）が
`x-growth-company`・`x-draft-post`・`x-idea-harvest` の3 Skill に別々の表として存在する。角度を1つ追加・変更するとき3箇所直す必要がある。

**修正案:** `prompts/angle-rotation.md` を新設して角度定義・狙い・ローテーションルールを一本化し、3 Skill は「Read: prompts/angle-rotation.md」の参照1行に置き換える。（prompts/ を正典とする CLAUDE.md の原則とも一致する）

### 3-3. 表現安全ルールの三重記載

`x-draft-post` の「表現の安全」5項目（未実装断定/オカルト/専門語/UI誇張/リンク主役）が、`x-risk-check` のチェック項目（日本語4項目）および `prompts/banned-patterns.md` と実質重複。

**修正案:** `banned-patterns.md` に「未実装断定」「オカルト・迷信」「専門語の壁」「UI動作の誇張」「リンク主役」をセクション追加して正典化し、`x-draft-post` / `x-risk-check` は参照のみにする。生成側と検査側が同じリストを見ることで「書いてから弾かれる」往復も減る。

### 3-4. 採点配点のハードコード重複

`x-score-post` が配点（20/20/15/15/10/10/10）を Skill 内に直接持っており、`prompts/scoring-rubric.md` の表と重複。今は一致しているが、rubric を調整したとき Skill が古い配点で採点し続けるリスク。

**修正案:** Skill からは配点数値を削除し「配点・判定閾値は scoring-rubric.md に従う」に変更。出力 JSON スキーマだけ Skill に残す。

### 3-5. `write-article` Skill がリポジトリの目的外

「AIツール・サービスのアップデート記事執筆」用で、PachiTracker X運用と無関係。しかもトリガーが「『記事を書いて』などの記事執筆依頼」と広く、**X運用の長文コンテンツ（note等）を頼んだときに誤発動して95点採点パネルなど別ワークフローが走る恐れ**がある。

**修正案:** 別リポジトリへ移動（推奨）。この場で使い続けるなら、description を「AIツール紹介記事専用。PachiTracker関連コンテンツには使わない」と限定する。

### 3-6. 重複ではないと確認したもの（現状維持でよい）

- `x-reply-assistant`（自分の投稿への返信）と `x-reply-outreach`（他人の投稿へのコールド返信）— 目的・制約が別物で、相互参照の注意書きも既にある。分離は正しい。
- `CLAUDE.md` と `AGENTS.md` の分担 — 「戦略の正典は AGENTS.md、実行ルールは CLAUDE.md」と明文化済みで矛盾なし。
- `x-growth-company`（統合）と個別 Skill の併存 — QUICKSTART の早見表で使い分けが明確。ただし §3-2/3-3 の共通部分を prompts/ に逃がせば統合 Skill は薄くなる。

## 4. 運用方向の改善提案（Phase 0 向け）

### 4-1. 統計ルールに Phase 0 例外を設ける【最重要】

現行ルール: imp<500 は「保留（低n）」、ランキングは K=500 の経験ベイズ縮小、型×時間帯セルは n≥2 必要。
実績: 投稿インプは 50〜160。**全投稿が保留になり、縮小率は prior にほぼ吸着して差が消え、週次レビューが構造的に何も言えない。** ルール自体は正しい（将来必要）が、適用時期が早すぎる。

**修正案:** `scoring-rubric.md` と `x-weekly-review` に「Phase 0（平均imp<500の間）」の判定モードを追記:
- 率ではなく **絶対数**（profile_visits・replies・follows_gained・詳細クリック）と定性シグナル（どの1行目で反応が来たか）で仮説を立てる
- 縮小率ランキングは「参考出力」に格下げし、imp が安定して500を超え始めたら現行ルールへ自動復帰（weekly_review.py に平均impで分岐を追加）
- 「勝ち仮説は週1つだけ」の原則はそのまま維持

### 4-2. リプ周りの計測を投稿と同格に引き上げる

7日1万インプの主源泉がリプ周りである以上、週次レビューが `post_log.csv` しか見ないのは片目運用。

**修正案:**
- `x-reply-outreach` の「投稿後」手順に **翌日 got_reply / profile_visit（推定でなく確認できた分）/ follow を `npm run reply-log` で埋める** ことを必須ステップとして明記（現状ログは全行空欄）
- `x-weekly-review` の Read に `reply_outreach_log.csv` と `reply_mix_report`（既存スクリプト）を追加し、「型別の返信獲得率」「リプ周り経由と推定されるフォロー増分（日次フォロワー差分 − 投稿由来）」を週次に含める
- 判断基準: 当面の主KPIを「リプ周り返信獲得率 × プロフ遷移」に置き、投稿は角度検証・信頼の土台として運用（戦略の変更ではなく、フェーズに合わせた計測の重心移動）

### 4-3. 固定ポストの導線検証

固定ポスト（460imp・4いいね）は思想の言語化として良いが、締めが「作っています」で止まりプロフ遷移後の次アクションがない。**β募集予定への言及 or「進捗はこのアカウントで」の一言を足す案を次回 `x-draft-post` で3案比較する**ことを提案（bio には「βテスター募集予定」があるので、固定ポストと bio の役割分担を決める）。

### 4-4. データ品質の小修正

- `data/post_log.csv` に post_type / time_slot が空の行（week00-p1, week01-p2b, week01-p4b）。セグメント集計から静かに漏れる。**値を補完するか、notes に「集計対象外（理由）」を明記**する。
- `docs/operating-manual.md:18` の `prompts/hook_examples.md` は存在しないファイル。→ `prompts/post-patterns.md` に修正（x-weekly-review の反映先とも一致させる）。
- operating-manual の Daily Workflow 手順1「backlog にネタを追加」に `x-idea-harvest` の言及がない。→ 「（`/x-idea-harvest` で生成可）」を追記。
